## Analysis

<!-- analysis: written by hand; kept when this report is rendered again -->

### In short

On the same machine, in one sitting, with the server pinned to the same two cpus, 5.0 did the same work as 4.1 (the same rows, features and writes, with no failed request) for 55 to 60% of 4.1's server CPU and a quarter of its SQL statements on the busy board (0.25× in board-steady, 0.22× in board-burst; 0.80× in reconnect-storm, 0.12× in fat-read), and answered the board query and `updateTask` 3 to 5 times faster at p95 under load. It sent almost as many bytes (0.89×) and blocked its event loop longer at the tail (p99 1.7× to 3.7×). Three of the four numeric targets are met; bytes per write is missed by a wide margin. The listeners target is met as stated (constant in the number of methods), though this small app's 5.0 sockets carry 5 more listeners than its 4.1 sockets.

The 5.0 app (`bench/apps/v5`) is the 4.1 app rewritten the way the 5.0 README teaches, with one deliberate departure from 5.0's defaults: its socket rate limiter allows 1,000 events per minute per socket instead of 100 (see "The default rate limiter" below). Everything else is at its default, including the console logger and the in-process change log.

### Where 5.0 is worse, and why

- **Restore after a reconnect storm (968 ms p50 against 10 ms).** By design of the 5.0 client, not a server cost. After a reconnect, the client resumes rows and collections by revision at once (live restore 2.3 ms p50 and 8.1 ms p95, against 10 and 26 ms; no snapshot served), but it refetches watched queries after a random delay of up to 2 s, so that a fleet of reconnecting clients does not hit the server in one burst (RFC 0003 section 11.3, `refetchAfterReconnect`). The restore time stops when the board query has been read again, so it measures that delay. Cached data stays on screen meanwhile, and the board query's rows can be up to 2 s stale. `lastRestoreSeconds` (3.73 against 2.00) is the same delay on the last viewer to drop.
- **Event-loop delay (p99 1.7× in board-steady, 3.7× in board-burst, about 5× in fat-read; max 2.2× to 3.1×).** The cost of `share: "all"` on the board query. One run's result goes to every call that joined it, and those replies are encoded and written back to back in one synchronous stretch: in the 5.0 profiles the longest busy stretches are 30 to 50 ms per fat-read round and 60 to 70 ms in board-steady, each about two thirds JSON encoding (`encodeAsString` and native stringify) and socket writes. 4.1 runs every call's queries separately, so its replies are spread out, at almost twice the total CPU. The worst p99 (29.8 ms) is far below the stall watchdog's 200 ms threshold, but it is a regression for everything else on the event loop. Follow-up 1.
- **Drain after the last write in board-steady (0.51 s against 0.26 s).** By design: the invalidation coordinator refetches a watched query at most once per 250 ms window, so the change from the last write is served when the window it arrived in ends; 4.1 debounced for 100 ms. The quiet check polls every 250 ms, which rounds both up.
- **Board query p99 in reconnect-storm (30.2 ms against 17.3).** The same shared-reply bursts, on the refetches that coincide after the reconnect delay (168 runs for 190 calls); the p95 (12.5 against 13.3 ms) is no worse.
- **Listeners per socket (20 against 15).** 5.0 registers a fixed set on every socket (14 events, 20 listeners, with or without subscriptions); 4.1 registers one per method and five per service: 15 for this app's 3 methods and 2 services, about 800 in Conveyor. 5.0's count is the same for 2 methods and for 200 (`packages/core/src/server/transports/socketio.test.ts`, "listeners per socket").
- **Peak RSS in reconnect-storm (502 MB against 428).** Not explained by these runs: 190 sockets each holding 60 rows, a collection and a topic cost about 17% more resident memory than in 4.1, while board-burst (0.87×) and fat-read (0.6×) used less. Follow-up 3.
- **Peak RSS in board-steady (526 MB against 523 and 524) and fat-read drain (7 ms against 1 to 2 ms):** worse than both 4.1 runs by amounts inside the repetitions' own spread; listed because the rule is "worse than both", not because they matter.

### Too noisy to compare

The two 4.1 runs disagree by more than 10% on 15 metrics, mostly p50 and p99 latencies in board-burst and the `updateTask` and delivery p50 in board-steady; their ratios prove nothing either way. Every metric a target uses agreed within 1% between the two 4.1 runs.

### Targets

- **Board query p95 in board-steady, at most half of 4.1: met** (34.6 ms against 122, 0.28×).
- **Bytes sent per write in board-steady, at most 30% of 4.1: missed** (10,381 KB against 11,725, 0.89×; board-burst 0.89× too). Each `getTasksByStatus` reply is 515.7 KB on the wire (120 full rows with their 4 KB plans, as fat-read measures it, the same for both versions), and every viewer reads it again after nearly every write: 20.0 reads per write for 5.0 (the coordinator's 250 ms window) against 22.3 for 4.1 (a 100 ms debounce that cancels and refetches). Subtracting those replies leaves about 51 KB per write for 5.0 (entity patches, collection deltas, change signals and write replies) against 261 KB for 4.1, about 19%; this split is an estimate from fat-read's reply size. The live updates are inside the target; the board query the app keeps is not.
- **Profile of the miss** (board-steady, one separately profiled repetition of each version with `--cpu-prof`, not the measured runs). 5.0's server was busy 21.3 s of 63.5 s: the reply path through Socket.IO took 60% of that (JSON encoding 26% in self time, WebSocket framing, engine.io and `writev` 24%), the Prisma client and pg 21%, garbage collection 8%, and the framework's own work besides sending a few percent. 4.1 was busy 33.5 s of 63.3 s: sending took 46% (including 6% in the stock parser's binary scan, which 5.0's JSON-only parser drops), the Prisma client and pg 36%, garbage collection 10%. In seconds, database client work fell from 12.1 to 4.4, JSON encoding from 8.1 to 5.6 and framing and writes from 6.4 to 5.1: 5.0 removed most of the database work and little of the reply volume. There is no small, clearly correct framework fix: the bytes are what the app asks for, and cutting them means sending less (follow-up 2). This card changes no framework code.
- **Snapshots served in reconnect-storm, at most 10% of 4.1: met** (0 against 11,590; all 190 collection subscriptions resumed and all 11,400 rows answered "not modified").
- **Board query handler runs in fat-read, 1 per round: met** (10 runs for 200 calls over 10 rounds; 4.1 ran 200).
- **Listeners per socket constant in the number of methods: met** (above).

### The default rate limiter

With 5.0's default socket rate limiter (100 events per minute per socket, which 4.1 did not have), one extra board-steady repetition, run with `rateLimit` removed from `bench/apps/v5/src/server.ts` for that run only (not committed), refused 100 of the 600 writes (each writer sends 120 a minute) and 50 board reads; the client's backoff then held each viewer's board query for the rest of the minute, so the viewers made 5,005 reads instead of about 12,000 and the server sent 2,514 MB. A busy board on 5.0 must raise `rateLimit`, or it will look cheaper only because it refuses work. Follow-up 4.

Since the pack G finale round the default is 600 events per minute per socket, which this workload stays under (a viewer reads the board about 240 times a minute, a writer writes 120 times), so `bench/apps/v5` now runs at the default; the runs in this report allowed 1,000.

### The load generator

The 5.0 client costs the load generator more than the hand-written 4.1 client: 23.6 s of CPU against 16.3 in board-steady (event-loop delay p99 12.9 ms against 4.8), and in board-burst an event-loop delay p99 of 38 ms against 4, because every viewer receives its shared board reply at the same moment and parses 516 KB of JSON. Client-side latencies for 5.0 include that lag, so they understate 5.0's improvement rather than overstate it.

### Follow-ups for later cards

1. **Shared replies in one burst (event-loop delay).** When a shared run settles, encode its result once for every call that joined it (the payload is the same JSON when no field tiers apply) and spread the writes over turns of the event loop. Expected: less CPU in board-steady and fat-read, and tail event-loop delay near 4.1's.
2. **Bytes per write.** The migration guide and the downstream briefs (pack G children 2 and 3) should steer boards from a fat query refetched on every change to the collection's index and items loaded by window, which send deltas only. Whether `watch` should also take a per-query refetch window for expensive queries is an owner question; it trades freshness for bytes. WebSocket compression (`perMessageDeflate`) for large replies, measured on both versions, is a separate experiment.
3. **Memory after a reconnect storm.** A heap snapshot of the 5.0 server after reconnect-storm, to find what holds the extra 70 to 80 MB.
4. **The default rate limit and busy boards.** Document it in the migration guide; whether the default should change, or exclude more of a board's traffic, is an owner question.

## Notes

- Medians of every scenario's repetitions, per run. `5.0 / 4.1` divides the 5.0 median by the mean of the two 4.1 medians; `4.1 drift` is how far the two 4.1 medians differ, as a share of their mean. A metric is marked worse when 5.0 is worse than both 4.1 runs, and noisy when the 4.1 drift is above 10%.
- 4.1 and 5.0 name some things differently on the wire; rows use one name for both: entity subscribe is 4.1's batchSubscribe and 5.0's qd:sub, collection subscribe is collection:subscribe and qd:col:sub, entity and collection unsubscribe likewise; topic watch (qd:watch) exists only in 5.0. A count of something only one version does (requests sent, handler runs, snapshots) shows 0 for the other and is marked `4.1 only` or `5.0 only`: a difference in design, never judged worse; any other metric a version does not have shows n/a.
- Per-write rows divide each repetition's bytes sent, SQL statements and server CPU by the writes it issued, then take the median.
- Client latency is timed in the load generator from emit to acknowledgement, only for calls answered successfully within the client's timeout; every other call is counted by kind, not timed. Calls abandoned because the client itself dropped the connection are counted separately and are not failures.
- Delivery is the time from a writer emitting updateTask to a viewer receiving that change (collection delta or entity update), on the load generator's single clock.
- Server CPU is process.cpuUsage() of the server process over the window. Event-loop delay is how late a 10 ms perf_hooks.monitorEventLoopDelay timer fired (the histogram value minus its 10 ms interval). Bytes are TCP bytes the server wrote, including HTTP and WebSocket framing.
- SQL statements are the Prisma client's query events: every statement the server sent, access checks and the reads that build live frames included.
- Machine noise comes from /proc: the time other processes spent on the server's pinned cpus during each window (those cpus' busy time minus the server process's own), and how busy the cpus the benchmark did not use were. Interrupt time on the server's cpus, mostly the benchmark's own network traffic, is kept apart in the result file.
- Every run starts a fresh server process on a freshly seeded database.
- Writes are open-loop: they are issued on schedule whether or not earlier writes have been answered, so a slow server cannot reduce the offered load.
- 4.1 runs: Clients speak the 4.1 wire protocol as the 4.1 React hooks do (bench/src/drivers/v4/viewer.ts lists the behaviors copied). Failed requests are timeouts (no answer within the 10 s the 4.1 hooks wait), error answers, and calls with no client timeout still unanswered when the window closed.
- 4.1 runs: Prisma batches findUnique calls made in the same tick into one statement, so the 60 per-row access checks and reads of a batchSubscribe cost a handful of statements rather than 180.
- 4.1 runs: The server logs with 4.1's defaults (two info lines per method call) to a file on local disk.
- 5.0 run: Clients run the 5.0 client itself (createQuickdrawConnection, liveDataOf, the invalidation coordinator and the cache session, wired as QuickdrawProvider wires them); bench/src/drivers/v5/viewer.ts lists what is reproduced of the query hook. After a reconnect, rows and the collection resume by revision at once and the watched board query is refetched after the client's random 0 to 2 s delay, so restore times include that delay; the live-restore times stop at the resumed rows and collection.
- 5.0 run: Failed requests are timeouts (no answer within the 5.0 client's default limit, the server's callTimeoutMs plus 2 s: 32 s), error answers (RATE_LIMITED included, whether the server sent it or the client refused a call while backing off), and calls still unanswered when the window closed. Subscription frames (qd:sub, qd:col:sub, qd:watch) are timed from emit to acknowledgement.
- 5.0 run: Handler runs count the calls that ran their own handler (a call that joined a shared run of getTasksByStatus is not one) and the subscription frames the server received, one per frame however many ids it named. Snapshots served count collection pages and entity rows sent; resumes and not-modified rows are counted apart.
- 5.0 run: The server logs with 5.0's defaults (the console logger: one debug record per call) to a file on local disk. Its socket rate limiter allows 1,000 events per minute per socket instead of the default 100, which would refuse part of this workload (4.1 had no limiter).
