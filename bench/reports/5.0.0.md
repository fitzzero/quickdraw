### In short

On the final code (5.0.0-rc.6), on the machine and cpus the first measurement used, in one sitting: 5.0 did the same work as 4.1 (the same rows, features and writes, with no failed request) for about half of 4.1's server CPU in every scenario (0.53× in board-steady, 0.50× in board-burst, 0.61× in reconnect-storm, 0.41× in fat-read) and a third of its SQL statements on the busy board (0.36× in board-steady, 0.23× in board-burst; 0.81× in reconnect-storm, 0.12× in fat-read), and it answered the board query and `updateTask` much faster at p95 under load: 6.5× and 8.7× faster in board-steady, 2.1× and 2.3× in board-burst (where the two 4.1 runs disagree on `updateTask` by 29%). Its event loop is no longer slower than 4.1's on the busy board (p99 0.80× in board-steady), but it still is at the tail in board-burst (p99 1.21×) and in fat-read (2.6×, where the two 4.1 runs disagree by 25%). It sends almost as many bytes (0.89×), the one numeric target it misses, because the app keeps a fat board query that every viewer reads again after each write. Three of the four numeric targets are met, and the listeners target is met as stated (constant in the number of methods), though this small app's 5.0 sockets carry 5 more listeners than its 4.1 sockets.

The 5.0 app (`bench/apps/v5`) is the 4.1 app rewritten the way the 5.0 README teaches, with every option at its 5.0 default: the socket rate limiter's 600 events per minute (the first measurement allowed 1,000; see "The default rate limiter"), the console logger and the in-process change log.

### Since the first measurement

This report replaces the first comparison, measured on 5.0.0-alpha.0 on 2026-10-04, before the pack G finale round; its files are in the git history of `bench/reports/5.0.0.md`, `bench/baselines/5.0.0.json` and `bench/comparisons/5.0.0/`. The 4.1 runs of the two sittings agree within 1% on server CPU, bytes and SQL statements, so the machine measured the same both days. The 5.0 metrics that moved most, each by more than its repetitions' spread (rc.0's three repetitions and this run's do not overlap), and below the table why every metric that moved did:

- **A shared run's reply is encoded once per group of callers** (the pack G finale round; `packages/core/src/server/pipeline/replies.ts`). At rc.0 each caller's reply was encoded on its own: twenty viewers joining one run meant twenty encodings of the same 516 KB back to back. In a separately profiled board-steady repetition, encoding replies now takes 1.9 s of the server's busy time against 5.6 s at rc.0 (the profile table under "Targets"). The board query's and `updateTask`'s latency, delivery and the event-loop delay fell by a third to a half in board-steady, and in board-burst too but for the board query's p99 (below); fat-read, 20 identical calls a round, uses a quarter less CPU, holds its event loop half as long and finishes a round in 28.5 ms against 35.8; and reconnect-storm's board query p99 (14.8 ms against 30.2) is no longer worse than 4.1's.
- **More board query runs, so more SQL statements per write.** A call joins a shared run only while the run is in flight. In board-steady 5.0 ran the board query 3,943 times for 12,007 calls, against 2,397 times at rc.0, and each run sends 12 statements (a page and a count for each of the six columns). That is the whole difference: in every repetition of both runs, the statements besides the board query's runs number 15,007 to 15,023 (one access check per board query call and 5 per write), so nothing per write changed. Most likely fewer calls join because the event loop is free now: at rc.0 each burst of per-caller encoding held it for tens of milliseconds while the next refetches queued, and those then started together and shared one run; now each is served as it arrives. Server CPU per write is what it was at rc.0 (33.0 ms against 33.9, inside the repetitions' spreads of 5.7% and 8%): the encoding saved pays for the extra runs. The same holds on a smaller scale in board-burst (45 runs against 36, 1,490 statements against 1,382, and 950 besides the runs in every repetition of both). Follow-up 5.
- **Board query p99 in board-burst (124 ms against 71.4 at rc.0; still 0.71× of 4.1's 175).** Not explained by these runs. Two candidates: more runs at once (45 against 36) queue for the pg pool's 10 connections, and a group's replies now reach its viewers together, all of them in the one load-generator process. The p95 (73.6 against 65.4 ms) is inside both runs' spread, and the server's CPU per write in that scenario fell 10%.
- **Microsecond revisions** add three digits to every revision on the wire: board-burst sent 44 KB more than at rc.0 (100 writes reaching 50 viewers in three frames each make 45 KB at three bytes a frame) and reconnect-storm 43 KB more (11,590 resumed rows and collections account for 35 KB of it), 0.02% and 0.04% of what either sent.
- **No change** beyond the spread: reconnect-storm (no snapshot served, live restore 2.3 ms p50, the watched query's restore with its 0 to 2 s delay, CPU, SQL), bytes per write (0.89× of 4.1, as at rc.0), peak RSS, and the drain after the last write.
- **Not visible in these numbers:** since rc.6 a schema output is reduced to its schema on every reply. The board query's output schema declares every column of a task, so nothing is dropped (fat-read sent 105,607,000 bytes, as at rc.0, to within 25 bytes), and the reduction's cost, about 0.16 µs a row, comes to under 0.1 s of board-steady's 19.8 s of CPU (3,943 runs of 120 rows), inside the 5.7% spread. rc.6 also records again a write that sets a value a row already holds; every write here changes a title, which carries the time it was sent, so no write was a no-op in either version. Positional `qd:stream` frames and the wire's ignore-unknown rule are not exercised by this board.

### Where 5.0 is worse, and why

- **Restore after a reconnect storm (1,056 ms p50 against 10 ms).** By design of the 5.0 client, not a server cost, and the same as at rc.0 (968 ms, inside both runs' spread). After a reconnect the client resumes rows and collections by revision at once (live restore 2.3 ms p50 and 9.3 ms p95, against 10 and 26 ms; no snapshot served) and refetches watched queries after a random delay of up to `reconnectJitterMs` (2,000 ms by default), so that a fleet of reconnecting clients does not hit the server in one burst (RFC 0003 section 11.3). The restore time stops when the board query has been read again, so it measures that delay; cached data stays on screen meanwhile, up to 2 s stale. `lastRestoreSeconds` (3.77 against 2.00) is the same delay on the last viewer to drop.
- **Event-loop delay in board-burst (p99 11.3 ms against 8.91 and 9.71) and fat-read (p99 8.82 ms against 2.94 and 3.78, which the two 4.1 runs disagree on by 25%), and its maximum in board-steady (20.4 ms against 13.2 and 14.5).** Down from 29.8, 19.2 and 42.2 ms at rc.0, and board-steady's p99 is now below 4.1's. What remains is most likely the rest of a shared run's replies, which still go out back to back when the run settles: for each one, `ws` and the framework's reply meter (`packages/core/src/server/transports/ack.ts`, which measures each reply for its call's completion record) each scan the 516 KB text for its UTF-8 length, then the socket writes it. In the board-steady profile each scan takes 2.8 s of the server's 18.9 s of busy time and `writev` 2.1 s, against 1.9 s for encoding. The worst p99 (11.3 ms) is far below the stall watchdog's 200 ms threshold. Follow-up 1.
- **Drain after the last write in board-steady (0.50 s against 0.26 s).** By design: the invalidation coordinator refetches a watched query at most once per 250 ms window, so the change from the last write is served when the window it arrived in ends; 4.1 debounced for 100 ms. The quiet check polls every 250 ms, which rounds both up.
- **Listeners per socket (20 against 15).** 5.0 registers a fixed set on every socket (14 events, 20 listeners, with or without subscriptions); 4.1 registers one per method and five per service: 15 for this app's 3 methods and 2 services, about 800 in Conveyor. 5.0's count is the same for 2 methods and for 200 (`packages/core/src/server/transports/socketio.test.ts`, "listeners per socket").
- **Peak RSS in reconnect-storm (506 MB against 428 and 423).** Still not explained: 190 sockets each holding 60 rows, a collection and a topic cost about 19% more resident memory than in 4.1 (17% at rc.0), while board-burst (0.87×) and fat-read (0.64×) used less. Follow-up 3.
- **Peak RSS in board-steady (535 MB against 521 and 523):** worse than both 4.1 runs by less than 3%, inside the repetitions' own spread (3.8%); listed because the rule is "worse than both", not because it matters.

### Targets

- **Board query p95 in board-steady, at most half of 4.1: met** (19.0 ms against 122, 0.15×; 0.28× at rc.0).
- **Bytes sent per write in board-steady, at most 30% of 4.1: missed** (10,370 KB against 11,709, 0.89×, as at rc.0; board-burst 0.89× too). Each `getTasksByStatus` reply is 515.7 KB on the wire (120 full rows with their 4 KB plans, as fat-read measures it, the same for both versions), and every viewer reads it again after nearly every write: 20.0 reads per write for 5.0 (the coordinator's 250 ms window) against 22.2 for 4.1 (a 100 ms debounce that cancels and refetches). Subtracting those replies leaves about 51 KB per write for 5.0 (entity patches, collection deltas, change signals and write replies) against 261 KB for 4.1, about a fifth; this split is an estimate from fat-read's reply size. The live updates are inside the target; the board query the app keeps is not, and that is the app's design rather than a framework cost: `MIGRATION.md`, "Boards", ports such a board to a collection, whose writes send each viewer a delta.

### The default rate limiter

At rc.0 the default socket rate limiter allowed 100 events per minute per socket (4.1 has no limiter), and one extra board-steady repetition run at that default (with `rateLimit` removed from `bench/apps/v5/src/server.ts` for that run only) refused 100 of the 600 writes (each writer sends 120 a minute) and 50 board reads; the client's backoff then held each viewer's board query for the rest of the minute, so the viewers made 5,005 reads instead of about 12,000 and the server sent 2,514 MB. A busy board would have looked cheaper only because it refused work, so the first measurement allowed 1,000.

Since the pack G finale round the default is 600 events per minute per socket, which this workload stays under (a viewer reads the board about 240 times a minute, a writer writes 120 times). These runs are at the default, and no request was refused.

### The load generator

The 5.0 client costs the load generator more than the hand-written 4.1 client: 23.9 s of CPU against 16.4 in board-steady (event-loop delay p99 12.6 ms against 4.5), and in board-burst an event-loop delay p99 of 31 ms against 5, because every viewer of a group receives its board reply at the same moment and parses 516 KB of JSON. Client-side latencies for 5.0 include that lag, so they understate 5.0's improvement rather than overstate it. Against rc.0 the load generator's board-burst lag fell (31 ms against 38) and fat-read's load generator used 11% less CPU (0.27 s against 0.30), with the 5.0 client's own changes since alpha.0 (not profiled).

### Follow-ups for later cards

1. **The rest of a shared run's replies (event-loop delay).** Since the pack G finale round a shared run's result is encoded once per group of callers. What remains: the group's replies are written back to back, and each is scanned twice for its UTF-8 length, by `ws` and by the reply meter. Measuring a shared reply once per group (its JSON text's length plus its envelope's) would remove the meter's scan, 2.8 s of the 18.9 s busy in the board-steady profile, and spreading a large group's writes over turns of the event loop would shorten the tail. Expected: less CPU in board-steady and fat-read, and event-loop delay in fat-read and board-burst near 4.1's.
2. **Bytes per write.** `MIGRATION.md` ("Boards") and the downstream briefs steer boards from a fat query refetched on every change to the collection's index and items loaded by window, which send deltas only. Whether `watch` should also take a per-query refetch window for expensive queries is an owner question; it trades freshness for bytes. WebSocket compression (`perMessageDeflate`) for large replies, measured on both versions, is a separate experiment.
3. **Memory after a reconnect storm.** Still open: a heap snapshot of the 5.0 server after reconnect-storm, to find what holds the extra 80 MB.
4. **The default rate limit and busy boards.** Done: the default is 600 events per minute per socket, which `MIGRATION.md` states, and this board stays under it.
5. **Sharing against latency.** A shared run that settles sooner gathers fewer joiners: 3,943 board query runs in board-steady against 2,397 at rc.0, 12 statements each. Whether a shared query should wait a few milliseconds for joiners, trading latency for statements, is an owner question.

## Notes

- Medians of every scenario's repetitions, per run. `5.0 / 4.1` divides the 5.0 median by the mean of the two 4.1 medians; `4.1 drift` is how far the two 4.1 medians differ, as a share of their mean. A metric is marked worse when 5.0 is worse than both 4.1 runs, and noisy when the 4.1 drift is above 10%.
- 4.1 and 5.0 name some things differently on the wire; rows use one name for both: entity subscribe is 4.1's batchSubscribe and 5.0's qd:sub, collection subscribe is collection:subscribe and qd:col:sub, entity and collection unsubscribe likewise; topic watch (qd:watch) exists only in 5.0. A count of something only one version does (requests sent, handler runs, snapshots) shows 0 for the other and is marked `4.1 only` or `5.0 only`: a difference in design, never judged worse; any other metric a version does not have shows n/a.
- Per-write rows divide each repetition's bytes sent, SQL statements and server CPU by the writes it issued, then take the median.
- Client latency is timed in the load generator from emit to acknowledgement, only for calls answered successfully within the client's timeout; every other call is counted by kind, not timed. Calls abandoned because the client itself dropped the connection are counted separately and are not failures.
- Delivery is the time from a writer emitting updateTask to a viewer receiving that change (collection delta or entity update), on the load generator's single clock.
- Server CPU is process.cpuUsage() of the server process over the window. Event-loop delay is how late a 10 ms perf_hooks.monitorEventLoopDelay timer fired (the histogram value minus its 10 ms interval). Bytes are TCP bytes the server wrote, including HTTP and WebSocket framing.
- SQL statements are the Prisma client's query events: every statement the server sent, access checks and the reads that build live frames included.
- Machine noise comes from /proc: the time other processes spent on the server's pinned cpus during each window (those cpus' busy time minus the server process's own), and how busy the cpus the benchmark did not use were. Interrupt time on the server's cpus, mostly the benchmark's own network traffic, is kept apart in the result file.
- Every run starts a fresh server process on a freshly seeded database.
- Writes are open-loop: they are issued on schedule whether or not earlier writes have been answered, so a slow server cannot reduce the offered load.
- 4.1 runs: Clients speak the 4.1 wire protocol as the 4.1 React hooks do (bench/src/drivers/v4/viewer.ts lists the behaviors copied). Failed requests are timeouts (no answer within the 10 s the 4.1 hooks wait), error answers, and calls with no client timeout still unanswered when the window closed.
- 4.1 runs: Prisma batches findUnique calls made in the same tick into one statement, so the 60 per-row access checks and reads of a batchSubscribe cost a handful of statements rather than 180.
- 4.1 runs: The server logs with 4.1's defaults (two info lines per method call) to a file on local disk.
- 5.0 run: Clients run the 5.0 client itself (createQuickdrawConnection, liveDataOf, the invalidation coordinator and the cache session, wired as QuickdrawProvider wires them); bench/src/drivers/v5/viewer.ts lists what is reproduced of the query hook. After a reconnect, rows and the collection resume by revision at once and the watched board query is refetched after the client's random 0 to 2 s delay, so restore times include that delay; the live-restore times stop at the resumed rows and collection.
- 5.0 run: Failed requests are timeouts (no answer within the 5.0 client's default limit, the server's callTimeoutMs plus 2 s: 32 s), error answers (RATE_LIMITED included, whether the server sent it or the client refused a call while backing off), and calls still unanswered when the window closed. Subscription frames (qd:sub, qd:col:sub, qd:watch) are timed from emit to acknowledgement.
- 5.0 run: Handler runs count the calls that ran their own handler (a call that joined a shared run of getTasksByStatus is not one) and the subscription frames the server received, one per frame however many ids it named. Snapshots served count collection pages and entity rows sent; resumes and not-modified rows are counted apart.
- 5.0 run: The server logs with 5.0's defaults (the console logger: one debug record per call) to a file on local disk. Its socket rate limiter is at its default, 600 events per minute per socket, which this workload stays under (4.1 had no limiter).
